El reto

Sensores que nadie cruza con la experiencia de los técnicos

Metal Tech, una planta metalmecánica ficticia de 240 personas, tiene sensores de temperatura, vibración, corriente, presión y caudal en motores, bombas, compresores, prensas, bandas y centros CNC. Pero la información se consulta aislada y las decisiones dependen de la experiencia de cada técnico.

El resultado son intervenciones tardías, falsas alarmas, repuestos cambiados sin necesidad y paradas no planificadas. El reto: formalizar ese conocimiento heurístico, unirlo a los datos y entrenar un modelo que prediga fallas y explique sus alertas.

Lo consultado

Una base de conocimiento construida con fuentes, sin entrevistas

Sin acceso a técnicos ni a normas de pago, un agente investigador consultó normas por fuentes públicas, literatura y datasets abiertos, y tomó cada decisión con su fuente. Un agente revisor la verificó de forma independiente.

      Método

      Cómo se construyó

      Metodología

      • ABP / ABPr: el problema de Metal Tech guía la construcción del artefacto.
      • CommonKADS para modelar el conocimiento; CRISP-DM para datos y modelos; ISO 17359 e ISO 13374 para ordenar el monitoreo de condición.
      • Agentes de IA con roles (investigador, revisor, datos, backend, frontend, documentación, QA) bajo un manual común, con bitácora de cada tarea y base de errores.
      • Once fases: conocimiento, ontología, datos, modelos, integración, explicabilidad, evaluación, prototipo, landing, ética y documentación.

      Datos sintéticos

      • Fallas con formas de degradación (lineal, exponencial, sigmoide, escalón, intermitente) y firmas incompletas.
      • Condiciones que imitan fallas, deriva de sensores y técnicos ficticios cuyo acierto depende del turno.
      • Partición temporal y una máquina de cada tipo reservada, que el modelo nunca ve.
      • Contrastados con AI4I 2020 y SKAB; ningún parámetro se ajustó mirando los resultados.

      Arquitectura

      Cuatro sistemas comparados

        Prototipo

        Una API y una web para probarlo todo

        Web demostrativa

        • Planta: estado de cada unidad según la fusión, frente a lo que de verdad pasaba.
        • Simulador: inyecte una falla, escriba lo que diría un técnico y vea el diagnóstico de cada sistema.
        • Explicación: peso de cada sensor, reglas con sus valores reales y alertas del periodo de prueba.
        • Base de conocimiento: reglas, FMEA, léxico, grafo de la ontología y decisiones.
        • Modelos, equidad e impacto, datos y bitácora: todas las métricas y el proceso del proyecto.

        API para otros sistemas

        • POST /diagnose: diagnóstico de M0, M1 y M3 con su explicación.
        • POST /simulate: genera una ventana con una falla y la diagnostica.
        • GET /kb/…: reglas, fichas de falla, léxico y grafo desde la ontología.
        • Documentación interactiva en /docs; la web usa la misma API.

        Se ejecuta en local: vea el manual de usuario en los recursos al final.

          Ética, equidad y límites

          Lo que el sistema no es

            • Datos sintéticos. Todo sale de un simulador calibrado con datasets públicos; las cifras no son desempeño en una planta real.
            • El técnico decide. El sistema recomienda y explica; no reemplaza la inspección.
            • Normas sin texto oficial. Los umbrales vienen de fuentes públicas y quedan marcados con su confianza.
            • Costos supuestos. El impacto económico se reporta en tres escenarios.
            • Sin datos personales. Técnicos anónimos y ficticios (Ley 1581 de 2012).
